HIVE CI SECURITY/QUALITY SETUP
==============================

Weekly schedule
---------------
GitHub scheduled security/quality and Advanced CodeQL checks run Sunday at 00:00 UTC.
Renovate is constrained to Sunday 00:00-02:30 Europe/London.
Normal push and pull-request CI continues to run immediately.

CI-specific secrets
-------------------
No new repository secrets are required for the added CI scanners.
OpenSSF Scorecard uses the workflow-provided GITHUB_TOKEN.
CodeQL uses GitHub's workflow token/security-events permission.

Existing deployment/operations configuration (not introduced by this CI work)
-----------------------------------------------------------------------------
The existing Koyeb deployment watcher still requires its existing KOYEB_TOKEN and KOYEB_SERVICE secrets.
Existing operations/ecosystem-smoke secrets and variables remain unchanged.

Dependency management
---------------------
Mend Renovate GitHub App is the dependency update owner.
Dependabot configuration is retained for repository/security posture visibility, but all update entries have open-pull-requests-limit: 0 so it does not create dependency PRs.
Renovate updates are manually approved for HIVE. This includes Python, Docker and GitHub Actions updates.
HIVE uses requirements.in as the direct production dependency source and requirements.txt as its compiled production lock. CI continues to enforce that the compiled lock matches requirements.in through scripts/verify_dependency_lock.py --compile. Any dependency PR must therefore include all generated/associated dependency files needed to pass that gate.

Added controls
--------------
- Advanced GitHub CodeQL for Python and GitHub Actions.
- Direct pinned Trivy CLI for filesystem/IaC and production Docker image scanning.
- Direct pinned Gitleaks full-history scan with redacted diagnostic artifact on findings.
- Direct pinned actionlint.
- Direct pinned Hadolint for Dockerfile.
- Direct pinned ShellCheck for HIVE operational shell scripts.
- Direct pinned Lychee link checking.
- Direct OpenSSF Scorecard CLI.

Supply-chain rule
-----------------
Native GitHub capabilities and approved GitHub Apps are preferred. Non-native scanners are installed and executed by repository-owned workflow code rather than third-party Action wrappers. Tool releases are version-pinned and checksum-verified where practical.

One-time GitHub CodeQL transition
---------------------------------
HIVE's supplied repository was marked as using GitHub CodeQL Default Setup. This update replaces that marker workflow with Advanced Setup for Python and GitHub Actions. In GitHub Security > Code security, disable CodeQL Default Setup before/when merging this workflow so only one CodeQL ownership model is active. Do not leave Default and Advanced Setup running in parallel.
Renovate lets pip-compile own requirements.txt; direct pip_requirements updates to that generated file are disabled to avoid duplicate/conflicting dependency PRs.

AUTONOMOUS PROVING-GROUP SETUP
- Scheduled window: Sunday 00:00 UTC; 2.5 hours reserved before the next repository starts.
- KiloConnect + Kilo Code Bot: authorise both GitHub integrations for this repository. Failed default-branch CI/deployment-watch runs create one deduplicated repair PR and invoke @kilocode-bot in PR context.
- Kilo may prepare dependency-manifest/lockfile/build fixes when evidence requires them, but all changes remain PR-only and must pass existing gates.
- Mergify config handles explicit superseded/obsolete PR cleanup only; it is not the merge authority.
- GitHub native branch/ruleset protections remain authoritative. Native Merge Queue can be enabled after required checks are confirmed stable.
- R2 Council ingestion/publishing is deferred to the HIVE Council implementation; no R2 credentials are introduced by this phase.
- Codecov and OWASP ZAP are intentionally NOT enabled.

- GitHub Actions must be allowed to create pull requests in repository Actions settings for the autonomous repair-PR workflow.
- Enable Kilo Code Reviews for this repository and enable REVIEW.md guidance in the Kilo Code Reviews configuration.
- Kilo Code Reviewer is review-only; the repair PR also invokes @kilocode-bot in PR context for implementation. Bot-generated PR review behaviour must be verified in Kilo settings because Kilo documents bot-created PRs as ignored by default by automatic Code Reviews.

AUTONOMY REPAIR GITHUB APP — REQUIRED FOR ZERO-TOUCH PR CI
- Create one private GitHub App, e.g. `Autonomy Repair Bot`, and install it on the repositories participating in autonomous repair.
- Repository permissions required by the App:
  * Contents: Read and write
  * Pull requests: Read and write
  * Issues: Read and write (required for repository labels used by the lifecycle rules)
  * Metadata: Read-only (automatic)
- The App does NOT need merge, deployment, secrets, administration or security-event write authority.
- Add repository variable `AUTONOMY_REPAIR_APP_ID` containing the numeric GitHub App ID.
- Add repository secret `AUTONOMY_REPAIR_APP_PRIVATE_KEY` containing the PEM private key generated for the App.
- `.github/workflows/autonomous-repair.yml` mints a short-lived installation token itself with OpenSSL/curl. No third-party token Action is required.
- This App token is used only for repair branch push, lifecycle labels and PR creation. Kilo then repairs inside the PR; existing CI/security/rulesets decide whether it may progress.
- Do not substitute `GITHUB_TOKEN`: GitHub deliberately makes PR workflow runs created/updated with `GITHUB_TOKEN` wait for maintainer approval.

AUTONOMOUS REPAIR AUTHENTICATION
- Required repository variable: AUTONOMY_REPAIR_APP_ID
- Required repository secret: the GitHub App private-key secret referenced by `.github/workflows/autonomous-repair.yml`
- The installed Autonomy Repair GitHub App needs Contents read/write, Pull requests read/write and Issues read/write for this repository.
- Repair PRs are created with the GitHub App installation token, not GITHUB_TOKEN, so pull_request workflows start without the manual approval loop applied to workflow-created GITHUB_TOKEN PRs.
- Mergify auto-merges an autonomy:repair PR only after the Autonomous repair marker gate succeeds and no active checks remain failed or pending. Kilo Code Review remains useful when it runs, but is not a mandatory named check because bot-generated PR review behaviour can vary. GitHub branch protection/rulesets remain authoritative.
- The old Renovate-specific deployment-revert PR path has been removed where present so a failed deployment produces one repair path rather than competing recovery PRs.

AUTONOMOUS MERGE SETTINGS
- Kilo Code Review should remain enabled for repository pull requests with REVIEW.md guidance, but autonomous merging does not depend on that named check being present.
- Mergify must have repository access. `.mergify.yml` auto-merges only validated `autonomy:repair` PRs after the repair-marker gate succeeds and all active checks are clear.
- Protect `main` with the repository's normal required checks. At minimum, the aggregate release/CI gate, the Autonomous repair marker gate, the repository security checks, and Kilo/Socket checks that are configured as merge gates should be required.
- Keep GitHub's workflow-approval security policy enabled; App-created repair PRs no longer depend on the workflow `GITHUB_TOKEN`.
- Enable GitHub's automatic deletion of head branches after merge to keep autonomous repair branches tidy.
CODEQL / TRUSTED PR AUTOMATION
- CodeQL open alerts are enforced by the CodeQL workflow and feed the autonomous repair/Kilo loop.
- The Autonomy Repair App creates the carrier PR with an installation token. GitHub documents that App-token-created automation PRs start normal pull_request workflows without the manual approval loop associated with workflow GITHUB_TOKEN-created PRs.
- Kilo implementation mode may update the carrier or open one linked implementation PR. Prefer a same-repository branch when supported; a separate Kilo PR must still pass every repository check and must link back to the carrier evidence.
- For public-fork workflow approval, use Repository Settings -> Actions -> General -> Approval for running fork pull request workflows from contributors. To remove the first-time-contributor prompt for the established Kilo bot without sending secrets/write tokens to forks, use the narrowest policy that fits: require approval only for first-time contributors who are new to GitHub. Keep fork secrets and write tokens disabled.
- If a new App-created carrier PR still asks for approval, stop and treat it as a configuration defect. If only a Kilo implementation fork asks, record it in the Sunday automation evidence rather than weakening fork security controls.
